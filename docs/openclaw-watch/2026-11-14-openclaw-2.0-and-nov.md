## What shipped

### 2026.8.1 — "OpenClaw 2.0" (30 Aug 2026)
Headline: distributed sessions, cloud workers with idle-suspend lifecycle, and a reworked memory and skill system.

- **Distributed/cloud sessions:** work moves to paired devices or cloud workers; warm machines and project seeds are reused across sessions; idle workers suspend and re-provision on next message.
- **Background memory consolidation ("dreaming"):** on by default — a model-backed job promotes provenance-qualified material into long-term memory and writes a Dream Diary; operators can see contributing sessions and issue `forget` for derived memory.
- **Skill self-learning:** strong lessons captured automatically; scanner-approved skills applied by default; Skill Workshop consolidates learned collections through a recoverable review flow.
- **Swarm (bounded parallelism):** experimental API fans out a limited set of parallel subagents and collects structured results.
- **Tool-result middleware / loop termination:** a middleware hook can end the agent loop after a completed tool, skipping the next model turn.
- **Headless agent exec:** `openclaw agent exec` runs against a chosen directory with temporary state and machine-readable results.
- **A2A 1.0 plugin:** opt-in authenticated text tasks and messages between configured peer agents.
- **Scoped standing approval for automations:** operator approves a recurring automation once for an exact operation; changes require fresh approval.

## What's notable

### 1. Background memory dreaming (2026.8.1)
Memory consolidation runs as an asynchronous background job — model-backed, provenance-aware, with a written log (Dream Diary). This is a major architectural shift from synchronous retrieval-only memory: the agent improves recall quality over time without blocking any turn.

### 2. Swarm / bounded parallelism (2026.8.1)
A first-class API for limited fan-out parallelism with structured result collection. The key design: parallelism is bounded (not unbounded) and results are typed. This keeps the orchestrator's complexity manageable while enabling genuine concurrent work.

### 3. Persistent-stream automations (2026.11.5-beta.1)
Scheduled work upgrades from fire-and-forget cron jobs to persistent streams — the automation carries execution context between invocations. This enables durable, stateful scheduled work (e.g. a monitoring loop that accumulates observations across runs).

### 4. Idempotent committed-input handling (2026.11.5-beta.2)
Retried or replayed inputs are acknowledged without starting duplicate agent turns. This is a correctness guarantee at the message boundary — critical for reliable async channels and multi-channel routing.

### 5. Tool-result middleware / loop termination (2026.8.1)
Middleware can end the agent loop after a tool completes, so an orchestration step that finishes its work doesn't burn a model turn to confirm it. Low-code way to implement early-exit patterns.

## What we can use in Lexicon

Ranked by estimated value/effort ratio (highest first):

### A. Idempotent input handling — `src/engine/queue.py` / `src/engine/runner.py`
**Value: HIGH / Effort: LOW**  
Lexicon's `src/engine/queue.py` processes incoming messages; `src/engine/runner.py` drives the agent loop. Neither currently guards against replayed or retried inputs producing duplicate turns. Add a committed-input log keyed on message ID before the runner starts a new turn — acknowledged duplicates return the existing turn ID without re-entering the loop. Pure correctness fix; no model calls.

### B. Background memory consolidation — `src/engine/memory/manager.py` + `src/engine/memory/episodic.py`
**Value: HIGH / Effort: MEDIUM**  
`src/engine/memory/manager.py` manages in-session memory; `src/engine/memory/episodic.py` handles episodic storage. Neither runs any background promotion job. Add an async consolidation task (tied to `src/cron/scheduler.py`) that runs after session end or on a timed interval: reads recent episodic entries, scores them against a promotion threshold, and writes promoted summaries with provenance tags into long-term memory. The Dream Diary write is a cheap append log — start there before building the scoring model.

### C. Tool-result middleware / loop exit — `src/engine/runner.py`
**Value: MEDIUM / Effort: LOW**  
`src/engine/runner.py` runs the tool-call loop. Add a middleware hook point after each tool result is collected; if the hook returns `done`, skip the next model call and return directly. This unblocks several current patterns that emit a final-answer tool but then waste a model turn receiving an empty response.

### D. Swarm / bounded parallelism — `src/engine/orchestrator.py`
**Value: HIGH / Effort: MEDIUM**  
`src/engine/orchestrator.py` orchestrates multi-step runs. Add a `swarm(tasks, max_concurrent)` primitive that fans out a bounded set of parallel sub-runners and collects typed results. The key constraint from OpenClaw's design: bound is enforced (not advisory), results are typed (schema-validated), and the swarm blocks the parent until all complete or one fails.

### E. Persistent-stream automations — `src/cron/scheduler.py` + `src/cron/store.py`
**Value: MEDIUM / Effort: HIGH**  
`src/cron/scheduler.py` and `src/cron/store.py` implement fire-and-forget scheduling. Upgrading to persistent streams means storing a stream record per automation alongside the cron entry and threading it into the execution context. Worth a spike once the idempotent input (A) and background memory (B) work lands.
