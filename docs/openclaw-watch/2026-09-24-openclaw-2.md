## What's notable

### 1. SQLite WAL split-brain prevention (v2026.8.1)
OpenClaw added explicit guard against WAL split-brain corruption, using rollback journaling on virtiofs/9p mounts and running snapshot verification in a separate process to prevent POSIX WAL lock drops. Also introduced schema-change arbitration: a Gateway now refuses competing shared-state schema changes while it owns the state directory.

**Why it matters:** Any agent framework storing conversation history or memory in SQLite without these guards can silently corrupt data under concurrent access or unusual mount types (common in containerised/cloud deployments).

### 2. Index-backed conversation full-text search (v2026.8.1)
Search across conversation history by exact words or phrases, backed by a persistent index updated at write time rather than full-table scan at query time.

**Why it matters:** At scale, scan-based search over transcript tables degrades badly. An FTS5 (or equivalent) index delivers sub-millisecond exact search with no schema refactor.

### 3. CPU-aware agent concurrency auto-sizing (v2026.8.1)
Default top-level concurrency is now derived from `os.cpu_count()` (or equivalent), bounded between 8 and 16. Previously a hardcoded constant caused under-utilisation on high-core hosts and overcommit on small ones.

**Why it matters:** A two-line change with meaningful correctness improvement across varied deployment targets.

### 4. Provider-managed context compaction (v2026.8.1)
Opt-in beta allowing the LLM provider to drive context compaction rather than the framework rolling its own summarise-and-replace loop. Preserves provider-side semantic continuity that client-side compactors often lose.

**Why it matters:** Lexicon currently owns its own compaction (`src/engine/context/compactor.py`). Delegating to provider APIs where available reduces maintenance burden and improves quality.

### 5. Gateway security hardening (v2026.9.5)
Three specific surfaces hardened: (a) command parsing — input sanitised before shell dispatch; (b) browser origin checking — rejects cross-origin requests at the gateway layer; (c) credential handling — credentials isolated to per-requester OAuth profiles rather than shared process state.

**Why it matters:** These are the three most common gateway-layer injection vectors. The pattern (parse → origin-check → per-requester credential scope) is directly portable.
