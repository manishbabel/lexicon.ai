## What's Notable

**1. Crash-safe cron persistence via SQLite WAL**
OpenClaw replaced its cron JSONL store with SQLite in WAL mode. Each state update is a single `UPDATE` row, not a full-file rewrite, so a crash mid-save leaves the previous row intact. A quarantine table holds the in-progress snapshot; the primary table only advances after the snapshot commits.

**2. Persistent outbox for channel delivery**
Rather than delivering channel messages inline (fire-and-forget), OpenClaw now writes outgoing messages to a SQLite outbox before attempting delivery. A background delivery worker reads from the outbox and marks items `delivered`. On restart, undelivered rows retry automatically. This turns the channel layer from best-effort to at-least-once.

**3. Approval queue with fair scheduling**
A new approval notification pipeline lets an agent pause a run, emit a structured question (with option cards) to the user's channel, and resume only after a response is received. The queue is FIFO per-agent with priority boosting for long-waiters. Approval history is persisted alongside episodic memory.

**4. In-process llama.cpp with RAM gating**
Local model inference runs as an in-process thread pool (not a subprocess) using llama.cpp bindings. A RAM gate is configured per-model; if available RAM drops below the threshold the gate rejects new inference requests (rather than OOM-killing the server). Useful for running on constrained hardware where cloud fallback is expensive.

**5. MCP Apps: declarative tool-set binding**
Tool-to-agent binding moved from runtime imperative code to a declarative TOML manifest (`mcp-app.toml`). Each app declares its tool list, the agent personas that can use it, and a dashboard label. This makes it easy to add/remove tools without touching agent code.

## What We Can Use in Lexicon

Ranked by value / effort (Low = easy, High = hard):

### 1. Atomic cron state updates (High value / Low effort)
**Problem:** `src/cron/store.py:122` `save()` does a full JSON rewrite on every state update. A crash between `write_text()` and OS flush corrupts `jobs.json` with no recovery path. `update_state()` at line 159 loads all jobs, modifies one, and writes all back — a TOCTOU hazard.

**Pattern to port:** Replace full-rewrite saves with atomic rename (`write to .tmp → os.rename`) — a two-line change that makes saves crash-safe without adopting SQLite. Long-term, adopt the SQLite WAL approach for per-row state updates in `src/cron/store.py`.

**File:** `src/cron/store.py:122`

---

### 2. Persistent outbox for gateway delivery (High value / Medium effort)
**Problem:** `src/gateway/session.py` holds all session state in-memory (`self._sessions` dict). When the process restarts, all active sessions and their pending messages are lost silently. For long-running cron-triggered sessions this is a data loss risk.

**Pattern to port:** Add a lightweight SQLite outbox in `src/gateway/` that persists in-flight messages before delivery, cleared on ack. Sessions that were active on shutdown can be replayed from the outbox on startup.

**File:** `src/gateway/session.py`, `src/gateway/server.py`

---

### 3. Approval-gated cron jobs (Medium value / Medium effort)
**Problem:** `src/cron/scheduler.py:177` `_execute_job()` fires unconditionally. For destructive or high-risk scheduled actions (e.g., auto-publishing), there is no way to require human approval before the job runs.

**Pattern to port:** Add an `approval_required: bool` flag to `CronJob` in `src/cron/store.py:69`. When set, `_execute_job()` emits a structured prompt via `CommandQueue` (STEER mode), waits for an explicit `yes`/`no` response before continuing, and logs the decision to episodic memory in `src/engine/memory/manager.py`.

**Files:** `src/cron/store.py:69`, `src/cron/scheduler.py:177`, `src/engine/queue.py`

---

### 4. RAM-gated local LLM fallback (Medium value / High effort)
**Problem:** `src/engine/llm/router.py:75` only supports cloud backends (`litellm`, `openai`, `anthropic`). There is no offline/local inference path.

**Pattern to port:** Add a `llama_cpp` provider to `PersonaLLMRouter._get_provider()` backed by `llama-cpp-python`. Gate activation on a configurable `local_llm_ram_mb` setting — if free RAM is below the threshold, router falls through to the configured cloud provider instead of hard-failing. Useful for on-device privacy or cost control.

**Files:** `src/engine/llm/router.py:75`, `src/engine/llm/provider.py`

---

### 5. Declarative tool-set manifests (Medium value / Medium effort)
**Problem:** `src/engine/tools/registry.py` registers tools imperatively in Python. Adding a tool to a specific agent persona requires code changes.

**Pattern to port:** Introduce a `tools.toml` manifest (loaded by `setup.py`) where tool-to-persona bindings are declared. The registry reads the manifest at startup rather than relying on hard-coded `register()` calls. This aligns with OpenClaw's MCP Apps pattern and makes tool sets configurable without deploys.

**Files:** `src/engine/tools/registry.py`, `src/engine/tools/setup.py`
