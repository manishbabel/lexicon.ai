## What's notable

### 1. SQLite-first persistence for cron + channel state (v2026.6.1)
OpenClaw migrated cron jobs, plugin install indexes, iMessage monitor state, and Discord thread bindings from flat files to SQLite. Concurrent writers are serialized per-store to prevent `SQLITE_BUSY`. Run-log tables are retained for backwards compatibility.

### 2. Interrupted tool-call recovery (v2026.6.1)
The runtime now handles mid-run interruptions — stale session bindings, compaction handoffs mid-turn, auth-profile failover — without data loss. The key mechanism is atomic auth-profile writes paired with an explicit failure-dispatch path that re-queues the pending work.

### 3. Skill proposal / versioning system (v2026.6.1)
Skills gain a `pending_proposals` queue: changes are staged with versioned, dated frontmatter before being approved into the live registry. Rollback metadata is stored alongside each approved change.

### 4. Gateway stable repair path (v2026.7.1)
Instead of restarting indefinitely, a Gateway that fails repeatedly now enters an explicit repair state: logs the stable failure reason, waits for operator intervention, and resumes from a known checkpoint. Prevents thrashing and data divergence between Gateway restarts.

### 5. Event-driven cron wakeup (v2026.7.1)
Scheduled jobs can declare a change-predicate; the scheduler skips the run if the predicate returns false (nothing changed). Reduces unnecessary LLM turns for polling-style cron jobs.

## What we can use in Lexicon

Ranked by value/effort ratio. All file paths verified to exist in the repo.

### ★★★ 1. SQLite for `CronJobStore` — High value / Medium effort
**File:** `src/cron/store.py`

`CronJobStore` currently serialises everything to `~/.lexicon/cron/jobs.json` via a full-rewrite on every `save()`. Under concurrent gateway + CLI activity this is a race condition. OpenClaw's pattern: move jobs and run-log entries to a single SQLite DB using `aiosqlite`; write per-row rather than whole-file; retain a JSON export path for human inspection.

### ★★★ 2. Gateway restart loop protection — High value / Low effort
**File:** `src/gateway/server.py`

The FastAPI lifespan context currently has no circuit-breaker for repeated startup failures. Port OpenClaw's repair-path pattern: track consecutive startup errors, enter a `REPAIR` state after N failures, and surface a structured error rather than looping. Likely ~30 lines wrapping the lifespan `asynccontextmanager`.

### ★★ 3. Interrupted tool-call recovery in runner — High value / High effort
**File:** `src/engine/runner.py`, `src/engine/runtime.py`

The runner's `run()` method (`src/engine/runner.py:30`) has no explicit mid-turn recovery path — a compaction handoff or session-binding failure mid-run drops the in-flight work. Port OpenClaw's pattern: checkpoint the run state before dispatching tool calls, re-queue on `asyncio.CancelledError` or binding mismatch, and surface the failure via the existing `trigger_hook` path in `src/engine/hooks/registry.py`.

### ★★ 4. Skill proposal staging — Medium value / Medium effort
**File:** `src/engine/skills.py`

Skills are currently loaded and live-activated from the registry with no staging layer. OpenClaw's Skill Workshop pattern (versioned frontmatter + `pending_proposals` queue + CLI review before activation) prevents bad skill definitions from going live silently. Port the frontmatter schema and a simple `pending/` sidecar directory before activating.

### ★ 5. Secrets scrubbing in logger — Medium value / Low effort
**File:** `src/shared/logger.py`

OpenClaw's v2026.7.1 hardening keeps "passwords and tokens out of more logs". Add a `SensitiveFilter` log filter that redacts patterns matching `Authorization:`, `Bearer `, `api_key=`, and common token lengths (>40 char hex/base64) before any log handler emits the record.
