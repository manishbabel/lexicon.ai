## What's Notable (Patterns)

### 1. Change-based scheduling wakeup (2026.7.1)
Cron and scheduled automations can skip a fire when no relevant state has changed — the scheduler short-circuits before spinning up a session. This eliminates idle execution cost for high-frequency heartbeats.

### 2. Turn persistence after restart (2026.10.5-beta.3)
Interrupted turns — including subagent work, automation turns, and streamed replies from killed workers — resume automatically after a Gateway restart. History is preserved; the session re-enters mid-turn rather than starting over or silently dropping output.

### 3. Non-blocking cron state writer (2026.10.5-beta.3)
The cron subsystem no longer holds the state-DB write lock while waiting on the host. Previously this caused locked-database errors during concurrent updates or restarts. The fix decouples the lock from I/O wait.

### 4. One-shot automation failure notice (2026.10.5-beta.3)
When a one-shot cron job reaches a terminal failure it now emits a failure notice rather than disabling silently. Operators get observability into failed runs that previously disappeared into the void.

### 5. Async tools outside the event loop (2026.9.2)
Long-running tool calls (transcript prep, durable history reads) are dispatched outside the Gateway's main event loop, preventing head-of-line blocking when large context operations stall other sessions.

## What We Can Use in Lexicon

Ranked by value / effort (HIGH > MEDIUM > LOW). All file paths verified against `src/`.

### A. Non-blocking cron state writer — HIGH value / LOW effort
**File:** `src/cron/store.py`
The write-lock scope in the cron store should be narrowed so it is released before any I/O wait (e.g., a host call or DB flush). This mirrors the OpenClaw fix and prevents locked-state crashes during concurrent scheduler runs.

### B. One-shot failure notice — HIGH value / LOW effort
**File:** `src/cron/scheduler.py`
Add a terminal-failure branch to the one-shot job executor. When a job exits with an unrecoverable error, emit a structured notice (log + optional channel routing) instead of silently removing the job. The notice payload should include job id, error, and last run timestamp.

### C. Change-based scheduling wakeup — HIGH value / MEDIUM effort
**File:** `src/cron/scheduler.py`
Add a pre-fire predicate hook to the scheduler. A heartbeat or cron job registers a `should_run(state) -> bool` callable; the scheduler calls it before spinning up the engine. Zero-change ticks (e.g. RSS feed unchanged, no new vault writes) never wake the runtime.

### D. Async tool dispatch outside gateway event loop — MEDIUM value / MEDIUM effort
**Files:** `src/engine/queue.py`, `src/gateway/server.py`
Long-running tool calls (large context compaction, transcript index rebuilds) should be dispatched to a background thread/executor rather than awaited inline in the gateway request handler. Prevents a slow `src/engine/memory/transcript_index.py` rebuild from stalling other gateway requests.

### E. Turn persistence on runtime restart — MEDIUM value / HIGH effort
**Files:** `src/engine/runtime.py`, `src/engine/runner.py`
Checkpoint in-progress turn state (current tool call, partial streamed output) to a durable store before a clean shutdown. On startup, `runner.py` checks for a pending checkpoint and resumes from it. High-effort because it requires a checkpoint schema and a safe resume path for tool re-entry.

## Spike Picks

**Spike 1 (this week):** Items A + B together — both live in `src/cron/` and neither requires new dependencies. Non-blocking store write + failure notice can ship as a single small PR.

**Spike 2 (next sprint):** Item C (change-based wake). Most impactful for Lexicon's scheduled agents. The `src/cron/defaults.py` file is the right place to wire default predicates for the built-in jobs.
