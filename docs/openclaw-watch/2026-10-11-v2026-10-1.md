## What's Notable

Five patterns worth tracking, in signal order:

### 1. Bounded embedding cache migration (2026.10.1-beta.2)
Embedding caches now migrate in bounded batches with oversized-row detection and reporting. Previously migrations were unbounded — a large store could OOM or time out silently. The new pattern: chunk the work, skip/report rows that exceed a size threshold, emit progress metrics. This is a durability and observability improvement for any system that stores vector embeddings.

### 2. Agent-to-agent peer-token validation (2026.10.1-beta.2)
Delegation calls now reject unresolved peer-token references before dispatch. Previously, a sub-agent could be handed a token reference that couldn't be resolved (e.g., the auth context expired between Chief enqueuing the call and the sub-agent starting). The fix validates the token at dispatch time rather than at first use. Also: a turn is recovered when its database worker exits before dispatch.

### 3. Per-agent memory scoping (2026.8.34)
Memory search results and shared-store access are scoped to the owning agent. Cross-agent memory leakage during concurrent delegation was a recurring bug class. The pattern: all memory-layer queries carry an `agent_id` filter; the store layer enforces it before returning results.

### 4. Cron schedule and output durability (2026.8.34–35)
Three separate hardening passes:
- Cron schedules survive upgrades, restarts, and Doctor repair (jobs are persisted before the scheduler restarts)
- Cron output is kept complete for delegated and CLI-triggered jobs
- Cron tool allowlists are preserved while automatic snapshots run

### 5. OpenAI Agents API integration (2026.9.7)
Native support for the OpenAI Agents API alongside the existing chat-completions path. Enables stateful, multi-turn agent runs through the API rather than a client-side loop. Also adds a beta "Sign in with ChatGPT" auth option — less relevant here, but the routing changes are.

## What We Can Use in Lexicon

Ranked by value delivered vs. effort to spike, each mapped to a file that exists.

| # | Pattern | Value | Effort | Files |
|---|---|---|---|---|
| 1 | Per-agent memory scoping | HIGH | LOW | `src/engine/memory/manager.py`, `src/engine/memory/search.py` |
| 2 | Bounded embedding migration | HIGH | MEDIUM | `src/engine/memory/episodic.py`, `src/engine/memory/search.py` |
| 3 | Cron schedule/output recovery | MEDIUM | LOW | `src/cron/scheduler.py`, `src/cron/store.py` |
| 4 | Peer-token validation at dispatch | HIGH | HIGH | `src/engine/orchestrator.py` |
| 5 | OpenAI Agents API path | MEDIUM | HIGH | `src/engine/llm/openai_provider.py`, `src/engine/llm/router.py` |

**#1 — Per-agent memory scoping** (`src/engine/memory/manager.py`, `src/engine/memory/search.py`)

`MemoryManager.recall()` currently fetches from all four layers (working, QMD vault, short-term, episodic) without filtering by which agent is calling. In a multi-agent orchestration run, sub-agents share the same `MemoryManager` instance and can surface each other's recent memories. The fix is to thread `agent_id` through `recall()` and enforce it at the per-source search calls. Low-effort because the data model already isolates memory files per session; it's a query-time filter only.

**#2 — Bounded embedding migration** (`src/engine/memory/episodic.py`, `src/engine/memory/search.py`)

If the episodic or short-term JSONL files grow large, a future migration or re-index runs unbounded. Adopting OpenClaw's pattern — chunk iteration with a per-row size cap, log/skip oversized entries — adds durability cheaply. The `transcript_index.py` path is also a candidate since it backs the QMD vector search.

**#3 — Cron schedule/output recovery** (`src/cron/scheduler.py`, `src/cron/store.py`)

`CronScheduler` uses APScheduler but delegates persistence to `CronStore`. The risk: if the process restarts between APScheduler's in-memory state and `CronStore`'s next flush, jobs are lost silently. OpenClaw's fix pattern is to write the job definition to the store *before* registering it with the scheduler, and to verify store integrity on `start()` before scheduling. One-day spike.

**#4 — Peer-token validation at dispatch** (`src/engine/orchestrator.py`)

The `Orchestrator` creates a fresh sub-agent runtime per delegation and runs it inline. There's no current check that the delegating agent's auth context (API keys, persona tokens) is still valid at the point the sub-agent starts. A pre-flight validation step before `AgentRuntime` construction would close this. High-effort because it requires deciding what a "peer token" looks like in Lexicon's model.

**#5 — OpenAI Agents API** (`src/engine/llm/openai_provider.py`, `src/engine/llm/router.py`)

`openai_provider.py` currently wraps the chat-completions endpoint. An Agents API path would allow persisting thread state server-side. Medium value because Lexicon already manages context via `MemoryManager`; high effort because it changes the session model.

## Spike Picks

**Spike 1 (highest ROI):** Per-agent memory scoping  
Touch `src/engine/memory/manager.py:recall()` to accept an optional `agent_id: str | None` parameter and pass it to `src/engine/memory/search.py`. Gate sub-agent calls in `src/engine/orchestrator.py` to pass their agent UUID. Estimated: one day.

**Spike 2:** Cron schedule/output recovery  
Audit `src/cron/scheduler.py:start()` and `src/cron/store.py` to ensure job definitions are persisted before APScheduler registration, and that `start()` validates store state before scheduling. Estimated: half-day.
