## What's Notable

### 1. On-exit cron schedule kind (beta)
Time-driven (`cron`, `every`, `at`) and event-driven (`on-exit`) scheduling now coexist. An `on-exit` job watches a subprocess and fires the agent when it exits cleanly. Useful for "run digest after nightly build" patterns without polling.

### 2. Scoped conversation capability profiles (beta)
Skills and tools are currently resolved globally per persona. This pre-release feature gates the available tool set per conversation — a read-only session can disable `vault_write`, a restricted persona can drop external tools entirely. Separation of skill availability from persona identity.

### 3. Provider fallback on usage limits / model-not-found (stable)
Instead of raising a hard error when the primary model is unavailable or over quota, OpenClaw now tries a fallback model from a configured chain. This is a config-layer change — no harness restart required.

### 4. Tool registry policy enforcement (stable)
A policy layer sits between the tool registry and handler dispatch: calls can be blocked, rewritten, or rate-limited after registry load. Specifically targets plugin tools that may be re-installed with different permissions.

### 5. Post-compaction instruction persistence + cleaner summaries (stable)
Compacted summaries now exclude raw tool blocks, media placeholders, and stale markers — reducing the risk of hallucinated context. Separately, repeated system-level instructions (e.g., injected mid-conversation by a skill) survive compaction.

## What We Can Use in Lexicon

Ranked by value / effort ratio. Each suggestion is grounded in a file that exists in the repo.

### ★★★ Provider fallback chain — HIGH value / LOW effort
**Why:** `src/engine/llm/router.py:43-65` `PersonaLLMRouter.resolve()` raises `ValueError` immediately when the resolved model is missing or the provider rejects it. Lexicon has no retry path.
**What to do:** Add an optional `fallback_model` (and optionally `fallback_provider`) to the per-persona config in `src/shared/config.py`. In `resolve()`, catch provider errors and retry with the fallback before re-raising. No harness changes needed.
**Files:** `src/engine/llm/router.py`, `src/shared/config.py`

### ★★★ On-exit cron trigger — HIGH value / LOW effort
**Why:** `src/cron/scheduler.py:138-173` `_build_trigger()` handles `cron`, `every`, and `at`. Adding `on-exit` completes the scheduling model — useful for post-build digests, post-deploy health checks, and test-completion runs.
**What to do:** Add a new `ScheduleType = "on-exit"` branch in `_build_trigger()` that launches an asyncio subprocess watcher. When the watched process exits (exit code 0), call `_execute_job()`. Store the watched command in `src/cron/store.py`'s `CronJob.schedule`.
**Files:** `src/cron/scheduler.py`, `src/cron/store.py`

### ★★ Tool registry policy layer — MEDIUM value / MEDIUM effort
**Why:** `src/engine/tools/registry.py` `ToolRegistry` has no interception point — `wire_into_runtime()` passes handlers directly to the runtime. A post-registry policy hook (block / rewrite by tool name pattern) would let us disable or gate sensitive tools (e.g., `vault_write`) without unregistering them.
**What to do:** Add a `ToolPolicy` dataclass (allow/deny/rewrite rules) and a `apply_policy()` method on `ToolRegistry` that wraps handlers before `wire_into_runtime()` is called.
**Files:** `src/engine/tools/registry.py`

### ★★ Post-compaction instruction persistence — MEDIUM value / MEDIUM effort
**Why:** `src/engine/context/compactor.py:113-158` `_compact()` protects only `PROTECTED_HEAD=2` and `PROTECTED_TAIL=6` messages. Skill-injected instructions that appear mid-conversation (after the protected head) are lost on compaction.
**What to do:** Before compacting `middle`, scan for messages matching a `[SYSTEM INSTRUCTION]` pattern and move them to a pinned-instructions list. Prepend them to the tail section so they survive. Also tighten `_sanitize_for_llm()` to strip media blocks (currently only strips `tool_result` and `tool_use`).
**Files:** `src/engine/context/compactor.py`

### ★ Scoped conversation capability profiles — HIGH value / HIGH effort
**Why:** `src/engine/skills.py:112-142` `SkillRegistry.load_all()` is global per persona. No per-session or per-conversation restriction exists. OpenClaw's scoped profiles are still pre-release and their API is unstable, so we should watch but not port yet.
**What to do:** Defer until v2026.7.1 stable ships. At that point, add a `CapabilityProfile` to `src/gateway/session.py` that filters `SkillRegistry.get_metadata()` and `ToolRegistry.wire_into_runtime()` outputs before each session starts.
**Files:** `src/engine/skills.py`, `src/gateway/session.py`, `src/engine/tools/registry.py`

## Spike Picks

**Spike 1 (this week):** Provider fallback chain in `src/engine/llm/router.py`. One method change, config addition, zero harness impact. High ROI if the LiteLLM provider starts hitting quota on heavy sessions.

**Spike 2 (this week):** On-exit cron trigger in `src/cron/scheduler.py`. The `_build_trigger()` dispatch is the natural insertion point; asyncio subprocess watching is straightforward. Unlocks a class of "run-when-done" patterns that polling can't match cleanly.

**Watch:** Scoped capability profiles. The pattern is right for Lexicon but the beta API may still shift. Re-evaluate when v2026.7.1 goes stable.
